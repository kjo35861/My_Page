# T08 인증 구현 설명서

## ① 무엇으로 붙였나
직접 구현했다. 표준 WebAuthn 프로토콜을 서버에서 직접 검증하되, 등록/로그인 옵션 생성과
서명 검증처럼 표준 스펙대로 정확히 구현해야 하는 저수준 암호 검증 부분만
`@simplewebauthn/server`(공개키 서명 검증 라이브러리, 등록·인증 로직 자체는 서버 라우터에서 직접 작성)와
`@simplewebauthn/browser`(브라우저의 `navigator.credentials.create/get` 호출을 감싸는 클라이언트 라이브러리)를 사용했다.
계정/패스키/일회용 질문/세션 저장은 Supabase(Postgres)를 사용했다.
세션은 JWT 같은 자체 서명 토큰이 아니라, 서버 DB(`sessions` 테이블)에 남기는 방식으로 만들었다
(로그아웃 시 즉시 폐기하기 위함 — ③, ④ 참고).

## ② 왜 그걸 골랐나
- 비밀번호 없이 공개키 방식으로 잠그는 것이 과제의 핵심이라, WebAuthn 표준을 그대로 쓰는 것이 맞다고 판단했다.
- 서명/챌린지 검증 같은 부분을 직접 구현하면 사소한 실수로 보안 구멍이 생기기 쉬워서,
  검증 로직 자체는 널리 쓰이는 라이브러리에 맡기고, "언제 계정을 만들지", "언제 질문을 재사용 못 하게 막을지",
  "누구의 자료만 보여줄지" 같은 서비스 로직은 직접 작성했다.
- DB는 이전 과제(T06/T07)에서 이미 써 본 Supabase를 그대로 사용해 새로 배우는 부분을 줄였다.

## ③ 어디를 어떻게 고쳤나
1번 과제의 `index.html`은 그대로 두고 `public/index.html`로 옮긴 뒤, 맨 아래(발자국 영역과 footer 사이)에
"비공개 자리" 섹션 하나만 추가했다. 인증 로직은 전부 새 파일에 작성했다.

- **등록**: `routes/auth.js`의 `POST /api/auth/register/options` → `POST /api/auth/register/verify`
  - 프론트: `public/index.html` 안의 `pz-register-form` 제출 핸들러
- **로그인**: `routes/auth.js`의 `POST /api/auth/login/options` → `POST /api/auth/login/verify`
  - 프론트: `public/index.html` 안의 `pz-login-form` 제출 핸들러
- **로그아웃**: `routes/auth.js`의 `POST /api/auth/logout` (세션 쿠키 삭제)
  - 프론트: `#pz-logout` 버튼
- **비공개 자료 조회**: `routes/private.js`의 `GET /api/private/me`, `GET /api/private/notes`,
  `GET /api/private/credentials`, `DELETE /api/private/credentials/:id`
  - 세션 쿠키 확인은 `lib/session.js`의 `requireAuth` 미들웨어가 모든 `/api/private/*` 요청 앞단에서 수행
- 일회용 질문(challenge) 저장·소진 로직은 `routes/auth.js`의 `saveChallenge` / `consumeChallenge` 함수
- 세션 발급/검증/폐기는 `lib/session.js`의 `issueSession` / `getUserId` / `clearSession`
  (쿠키에는 무작위 토큰 원문만 담고, DB에는 그 토큰의 해시만 저장 — 로그아웃하면 DB의 레코드를 지워
  같은 쿠키 값이 더 이상 통하지 않게 만든다)
- 신규 가입 시 계정(`users` 행)은 `register/options`가 아니라 **`register/verify`에서 서명 검증을 통과한 뒤에만**
  만든다. 그 전까지는 challenge에 `pending_username`만 임시로 들고 있다가, 등록이 취소되거나
  검증에 실패하면 challenge만 만료되고 users 테이블에는 아무것도 남지 않는다.

## ④ 안 열리는 것을 확인한 기록
아래 네 가지를 실제 요청/응답으로 확인했다. (세션·토큰 값은 가림)

**1) 로그인하지 않고 비공개 자료를 직접 요청**
```
GET /api/private/notes
→ 401 { "error": "로그인이 필요합니다." }
```
비교로, 로그인한 뒤 같은 요청은:
```
GET /api/private/notes  (Cookie: session=***)
→ 200 { "notes": [ ... ] }
```

**2) 남의 패스키로 로그인 시도**
계정 A의 아이디로 로그인 옵션을 받은 뒤, 계정 B의 패스키로 서명해 응답하면
`routes/auth.js`의 `login/verify`에서 `credential.id`가 A 계정의 `credentials` 테이블에 없어
아래처럼 거절된다.
```
POST /api/auth/login/verify { userId: "A의 id", credential: {"id":"B의 credential id", ...} }
→ 400 { "error": "이 계정에 등록되지 않은 패스키입니다." }
```

**3) 이미 쓴 질문(challenge) 재사용**
정상 로그인 한 번 성공 직후, 같은 challenge·서명 값으로 다시 `login/verify`를 보내면
`consumeChallenge`가 이미 `used=true`로 표시된 challenge를 찾지 못해 거절한다.
```
POST /api/auth/login/verify  (같은 credential 재전송)
→ 400 { "error": "로그인 요청이 만료되었거나 이미 사용된 질문입니다." }
```

**4) 패스키 삭제 뒤 그 패스키로 로그인**
`DELETE /api/private/credentials/:id`로 패스키 하나를 지운 뒤, 남은 패스키로는 로그인에 성공하고
지운 패스키로는 `login/verify`에서 credential을 찾지 못해 거절된다.
```
DELETE /api/private/credentials/{지울 id}  (Cookie: session=***)
→ 200 { "ok": true }

POST /api/auth/login/verify (지운 credential로 서명)
→ 400 { "error": "이 계정에 등록되지 않은 패스키입니다." }

POST /api/auth/login/verify (남은 credential로 서명)
→ 200 { "verified": true }
```

**5) 로그아웃 후 같은 세션 쿠키 값 재사용**
`/api/auth/logout`은 쿠키를 지우는 것과 별개로 서버 `sessions` 테이블에서 해당 토큰의 레코드를
삭제한다. 그래서 로그아웃 전에 복사해 둔 쿠키 값으로 다시 요청해도 서버에 레코드가 없어 거절된다.
```
POST /api/auth/logout  (Cookie: session=***)
→ 200 { "ok": true }

GET /api/private/notes  (같은 Cookie: session=*** 재사용)
→ 401 { "error": "로그인이 필요합니다." }
```

## ⑤ AI와 나
- **AI에게 맡긴 일**: WebAuthn 등록/인증 옵션 생성 함수와 서명 검증 함수의 정확한 파라미터 이름·타입
  (`@simplewebauthn/server` 버전별 API 차이 포함) 확인, Express 라우터/스키마의 기본 뼈대 작성.
- **내가 직접 판단한 일**: 어떤 데이터를 세션 쿠키가 아닌 요청 본문으로 받을지(신뢰 경계 결정 —
  비공개 자료 조회 시 `userId`를 클라이언트가 아니라 항상 세션 쿠키에서만 읽도록 정한 것),
  계정이 이미 있는데 로그인하지 않은 상태로 패스키 추가를 요청하면 거절하도록 정한 것,
  패스키를 다 지웠을 때 계정이 잠기는 것을 허용할지(허용하기로 정함, 아래 ⑥ 참고).
- **AI 제안을 따르지 않은 일**: 없음. 구조·보안 경계에 대한 제안은 내가 직접 검토해 대부분 그대로
  받아들였고, 크게 다른 방향으로 반대한 지점은 없었다.

## ⑥ 아직 못 막은 것
패스키를 마지막 하나까지 지우면 그 계정은 다시 로그인할 방법이 없다(백업 로그인 수단이 없음).
서버가 삭제 자체를 막지는 않으므로, 실수로 마지막 패스키를 지우면 그 계정의 비공개 자료는
영영 열 수 없게 된다. 이번 과제 범위에서는 복구 수단(이메일 복구, 관리자 재설정 등)을 만들지 않았다.
